# Vault batch copy to one phone directory: bounded extension contract

Status: revision 4, final design candidate for independent sign-off, 2026-10-16. Design only; no implementation or device execution. Production remains `ENABLED=false`. No real keys, user media, cloud provider, new dependency, new permission, or persistence grant is authorized by this document.

## 1. Outcome and existing owner

Select 1–8 authenticated Vault MP4 objects, choose ONE phone-filesystem directory using ONE `ACTION_OPEN_DOCUMENT_TREE`, explicitly confirm ordinary readable copies, then process the frozen list sequentially. Retain every Vault original for success, failure, cancellation, uncertainty, restart, and retry. A later item's failure never rolls back a successful prior child. No private-to-ordinary move, album substitution, sharing, or background auto-unlock.

Extend the existing `VaultRuntime` → `VaultMediaRuntime` helper, exact injected `AndroidVaultAuthentication`, `AndroidVaultStore`, and `AndroidVaultPhoneFiles`. Keep ONE active `COPY_OUT` item, one controlled reader, one source ciphertext anchor, one sink/readback handle lane, the existing IO publication gate, actual-close ledger, and whole-snapshot CAS. Extract the existing `confirmCopy` byte-transfer body to a private same-helper function used by single and batch paths; do not create a second copy engine or ordinary Library export row.

Current source actually has a scalar `VaultMediaJournal`, `newOperation` gated by its terminal phase, one outstanding picker, an in-memory target identity map, and a non-tree local-file profile. These must be extended explicitly; a loop around today's `beginCopy` would launch N pickers and lose batch evidence.

## 2. Finite selection and budget

- `MAX_ITEMS=8` is this slice's bounded implementation limit, not a claimed limit in the original product requirement; immutable ordered identities; reject empty, duplicate identities, mixed vault/catalog revisions, stale/missing sources, or count overflow before picker/create. Reauthenticate all selected metadata at confirmation. The immutable selected catalog revision is audit evidence, not an eternal root binding: after credential reset/reseal, authenticate the current catalog and require each original object/generation still exists unchanged before starting an untouched row. Bind its fresh scalar phase/ref to the current authenticated catalog revision. Never substitute latest generations silently.
- Same per-file limits: 2 GiB plaintext, 64 KiB scratch, bounded zero-progress failures, existing Tink profile. No full media buffering or plaintext staging.
- One execution run shares the existing 30-minute monotonic deadline across all items; do not refresh it per item. At most eight explicitly started runs per batch, durably charged before work, bounds cumulative admitted work to 240 minutes. Automatic continuation after an ordinary clean item does not consume another run or refresh its deadline. Waiting for picker/authentication is not active decryption time. A deadline stops the run; another run requires explicit current user confirmation, never a timer. Eight runs is likewise an implementation budget rather than a product requirement. At that limit, retain every completed/retained result, reconcile the current item without new source IO, and mark untouched rows PAUSED_NOT_STARTED / budget exhausted. The user may put those untouched rows in a newly confirmed batch; never discard them or pretend they failed to export.
- Batch URI fields are bounded to 1,024 UTF-8 bytes each; generated batch/item/nonce/grant IDs use 32 ASCII hex bytes. Retain existing object-ID bounds. The same journal has an actual 16 KiB encrypted-envelope cap and 14 KiB plaintext cap despite the broader 64 KiB snapshot field cap. Preserve both existing caps. Before admitting the plan, canonical-encode its worst legal terminal shape (including one active target duplication); reject if it cannot fit. No truncation, cap widening, dropping old results, or partial admission. Directory metadata enumeration is bounded to the existing `FolderCreateIdentity.MAX_CHILDREN=1,000`, total ID bytes at most 1 MiB, and the current run deadline; overflow/loading/partial query means unsupported, before create.

## 3. One temporary tree capability

The same phone-files adapter owns one request identity for either a single-file request or a batch-tree request. The exact Activity callback must match the outstanding launched identity, pending batch, and selection epoch. Replayed/wrong callbacks confer no authority. The picker may background/lock Vault; retain only the selected directory capability, cover private UI, and require a fresh current unlock plus explicit confirmation before any source read or child creation.

Request `ACTION_OPEN_DOCUMENT_TREE`, read/write and prefix grant flags, and `EXTRA_LOCAL_ONLY=true`. Do not request/take persistable permissions in this slice. Requested flags are not proof: validate returned read/write bits and effective access, and recheck permission before each create/write/readback/publication/cleanup. No ordinary-folder default or grant registry is read/written. The root tree URI is canonical `buildTreeDocumentUri(authority, treeDocumentId)`, content-only, no query/fragment, no extra selected URIs. An exact tree document is a directory, nonvirtual, and advertises `FLAG_DIR_SUPPORTS_CREATE`.

Reuse the fixed trusted profile: authority `com.android.externalstorage.documents`; package `com.android.externalstorage`; class `com.android.externalstorage.ExternalStorageProvider`; system/updated-system, Android-signature match, enabled/exported/grantUriPermissions, exact MANAGE_DOCUMENTS read/write protection. Tree ID must be a non-root `primary:` directory. No URI-to-filesystem-path conversion. Unknown/OEM/cloud/removable providers fail closed. `EXTRA_LOCAL_ONLY` alone never proves no upload. Honor platform disabled choices; no constructed URI bypass of Android 11+ root/Download/Android-data restrictions.

A tree grant covers a subtree. We deliberately create direct children only. `isChildDocument` proves ancestry, not direct parentage; validate returned child ID against a bounded immediate-child query of the selected directory, as well as exact tree binding and provider profile. A returned child must be nonvirtual `video/mp4`, not the directory, have real read/write grants, and advertise required write/delete capabilities. Directory support/profile is checked again per item.

## 4. Encrypted batch envelope and scalar item handover

Extend the existing encrypted `VaultMediaJournal` payload with optional `VaultCopyBatchState`, preserving version-1 decoding and legacy single-item bytes. Version 2 is used for batch payloads or the new explicit single-item OUTPUT_RETAINED outcome; encrypted header/AAD binds the batch ID and canonical immutable plan digest in addition to existing operation/vault/root/catalog bindings. No names, IDs, hashes, URIs, results, or tree tokens go into plain SQLite columns, saved UI state, logs, WorkManager data, or ordinary journals.

The batch state contains immutable batch ID, ordered object identities and per-row operation IDs, selected catalog revision, one optional exact tree record, fixed limits/profile version, durable run count, active index, stop/pause intent, and bounded per-row results. Each attempted item is still the top-level ordinary `COPY_OUT` scalar operation with the existing monotonic sequence. Allocate its sequence when activated; queued IDs confer no IO authority. Completed/aborted rows retain their exact target record/evidence/outcome; the active target stays in the scalar item. Capacity accounting includes temporary duplication at completion.

Transitions are checked by `VaultMediaJournalWire.requireSuccessor`: immutable plan/tree cannot be rebound; active index moves forward only; terminal prior results cannot change; at most one active row; no row can reactivate; no new operation bypasses a pending batch. Moving from a terminal scalar item to the next PREPARED scalar is one fresh whole-snapshot CAS preserving all prior results. Unrelated move/single-copy work stays busy while the batch is pending. Credential work is blocked only by live work, unknown mutation, or actual resource drain. Once locked and drained, existing master-password/recovery-code authentication and reset remain available, so a forgotten password cannot deadlock batch reconciliation. Credential reseal preserves the entire batch envelope; a fresh continuation authenticates current catalog and original object/generation identities, with the original selection revision retained as audit evidence.

Append two phases without changing existing ordinals: `CHILD_CREATE_INTENT` for batch child reservation, and terminal non-success `OUTPUT_RETAINED` for the single-item safety correction below. First item: PREPARED → PICKING_TARGET → [tree bound, still picking/waiting confirmation] → CHILD_CREATE_INTENT → TARGET_BOUND → existing SOURCE_VALIDATED → COPYING → VERIFYING → PUBLISH_INTENT → COMPLETE. Later items: PREPARED → CHILD_CREATE_INTENT → same engine. Tree-bind and result updates are authenticated journal transitions, not mutable UI fields. The CHILD_CREATE_INTENT scalar target is a generated reservation with null URI; its only permitted bind fills that exact returned URI while preserving operation/grant/nonce/flags, then becomes immutable. No parent phase or result is a transferable proof.

## 5. Child creation and the acknowledgement gap

1. Authenticate current batch/source metadata; establish current host/root/context and exact selected tree. Bound complete immediate-child IDs before create. Existing filenames are never replaced.
2. Persist `CHILD_CREATE_INTENT` with active operation ID, exact tree identity, fresh nonce, and selected source before calling the provider. Create exactly once with generated name `ESV-<nonce>.mp4`; filename adjustment by provider is allowed, filename is never identity.
3. On a returned URI, first register the exact returned target in the SAME adapter's identity ledger, then validate local/tree/direct-child/new-ID facts, then bind that exact child URI using the authenticated Vault journal CAS. No writer is opened before durable TARGET_BOUND. A returned pre-existing child ID, wrong directory/provider, duplicate target, or inconsistent query is rejected and is never written/deleted as owned.
4. Failed/null/throw/interrupted create without durable returned-child identity is UNKNOWN, not absence. If a return exists only in the live owner map, retain it for narrow cleanup after CAS inspection. After process loss, no name/nonce search, set difference, guessed URI, directory sweep, or repeat create may recover this item.
5. Once bound, run the unchanged entire-source authenticated discard pass, same-anchor streaming copy, real flush/close, full external length/SHA/EOF readback, release checks, exact PUBLISH_INTENT decision, and completion. No next item until this item's resources genuinely drain. Locked source/cancelled context cannot issue another decrypt/write/readback or late plaintext publication.
6. SAF children can be externally visible while incomplete. PUBLISH_INTENT is the app's verified irreversible completion decision, not an atomic filesystem visibility switch. UI must explain that incomplete ordinary copies may need manual attention.

## 6. Per-row results, cancellation, continuation, and retry

Exact scalar/result mapping: VERIFIED_COPY is COMPLETE. FAILED_NO_OUTPUT, FAILED_CLEANED, CANCELLED_BEFORE_START, CANCELLED_CLEANED and explicitly isolated UNRESOLVED_RETAINED are CANCELLED with the item's cancelRequested=true; this item-abort marker does not set the batch user-stop bit. PAUSED_NOT_STARTED rows have no activated transfer to replay. CLEANUP_REQUIRED remains nonterminal cleanup/reconciliation; FINAL_DECISION_PENDING retains PUBLISH_INTENT or the exact unknown proposal. PUBLISH_INTENT may only remain pending or become COMPLETE, never skip/cancel. Archive/cursor advance follows terminal whole-CAS readback and actual drain, never a UI outcome enum.

Rows distinguish `WAITING`, `ACTIVE`, `VERIFIED_COPY`, `FAILED_NO_OUTPUT`, `FAILED_CLEANED`, `CANCELLED_BEFORE_START`, `CANCELLED_CLEANED`, `PAUSED_NOT_STARTED`, `CLEANUP_REQUIRED`, `UNRESOLVED_RETAINED`, and `FINAL_DECISION_PENDING`. Only VERIFIED_COPY contributes to successful count. Preserve technical failure reasons without sensitive values. Partial success is an honest count plus per-row status, never all-success.

- A normal local source failure may continue to the next item only after confirmed no child, or exact child deletion plus real drain, and a durable terminal result. Shared permission/profile failure pauses the remaining queue instead of blindly creating failures.
- Current `decisionAccepted` is launch-scoped and must be refactored to an exact active-operation decision field: reset finalDecisionAttempted/accepted atomically at handover only after the prior terminal CAS and real drain, under the same gate and unchanged run deadline. A successful item must not disable cancellation of its successor.
- User Cancel sets stop intent before further scheduling, cancels the current context if no final decision won, and marks untouched items CANCELLED_BEFORE_START. Current cleanup is exact target-only, requires sufficient current target ownership evidence, and may require later unlock to durably record it; a present target with only URI/token/grant evidence is retained, not deleted. Already verified children are retained. A PUBLISH_INTENT winner is reconciled/preserved even if cancellation raced it.
- Lock/background/revocation stops new scheduling immediately and drains current resources. It does not discard the selected tree or authorize an automatic resume. Untouched rows remain PAUSED_NOT_STARTED; user may explicitly continue after fresh auth, real grant/profile validation, and prior-item resolution. All confirmation callbacks are process-local exact identities and cannot survive as authority.
- A user may explicitly skip a retained uncertain output and continue untouched rows only after the original whole-CAS outcome is resolved, no old IO/admission/close uncertainty remains, and a durable UNRESOLVED_RETAINED result revokes that item's write/delete/publish capabilities. Retirement requires the fixed store owner to validate the exact durable batch/row/target/outcome, reject any pending CAS, and the adapter to observe real handle drain; a caller-supplied enum or DTO is never proof. Explain that a possible incomplete file is being kept. This is administrative isolation, not proof of cleanup, and is forbidden for unresolved PUBLISH_INTENT/DB-CAS decisions. Never evict an unconfirmed owner to enable this action. The same scalar engine then advances to a fresh item; no second owner is introduced.
- Retry is explicit and creates a NEW batch/operation identity for selected eligible failed or never-started rows. No hidden retries; no in-place append/truncate/resume. VERIFIED_COPY rows are excluded by default. A prior exact output must be confirmed absent/cleaned before that row is eligible. UNRESOLVED_RETAINED is not retry-eligible; a separate clearly labeled export-again choice may warn of duplicate ordinary copies, but is deferred from this slice. A retry destination is one explicitly chosen directory for that new batch, not a mutable saved default.

## 7. Restart and grant reality

A stored URI is evidence, not a grant. Android temporary grants can outlive process death but do not create a new owner identity; never reconstruct runtime authority just from URI text or assume grants vanished. Restart is locked, never runs pending media work, and never replays child creation or copying. After explicit unlock, inspect the original complete CAS outcome first, authenticate the original batch, preserve completed rows, and request the exact same tree only if renewed access is needed. This is an explicit recovery reauthorization, not a per-item picker or silent destination change. Keep the original encrypted tree record/grant ID immutable. A fresh exact recovery request and selection epoch validate the newly returned same authority + treeDocumentId + canonical URI and actual flags/access, then register a new process-local authorization witness against that original record. The old grant ID/URI confers no authority, and the new witness does not rewrite the original record or revive old contexts.

Path-derived ExternalStorageProvider document IDs do not by themselves prove the same file incarnation after restart or a same-process replacement. Ordinary provider-mediated delete normally revokes the old document grant; this design does not claim all replacements retain grants. Uncovered cases include direct filesystem replacement, fresh recovery selection of a same-URI replacement, and child-ID reuse under a parent tree grant. This is source-supported conservative reasoning, not a device-reproduced defect. A renewed tree grant plus stored URI/name is insufficient to delete an uncertain partial child. Such output remains manual/unresolved unless independent exact-owner evidence exists; this slice adds no incarnation framework. A retained current-process capability preserves original ownership obligations, but is not itself file-incarnation proof. Destructive cleanup or recovery reopen requires independently sufficient current exact-target evidence. This slice adds no such incarnation framework: with only URI/token/grant evidence, confirm exact absence if provable; otherwise keep the present target for manual attention or explicit drained skip. Freshly selected replacement files are never adopted for old output deletion. Never query/find files by nonce to infer ownership. New WAITING children may proceed after explicit skip/preserve isolation under section 6; old completed children are never recopied or deleted.

A durably observed PUBLISH_INTENT can finish the existing app-level completion bookkeeping without source decryption or a new create. It records the verification that preceded the original decision, not a promise that an external user has not since modified/deleted the copy. If the final CAS remains unknown, keep FINAL_DECISION_PENDING and stop the batch. Persisted completed receipt remains completed even if a later external file disappears; the app does not recreate it automatically.

## 8. Narrow correction shared with the existing single-item engine

Inspection of current AndroidVaultPhoneFiles.cleanup found registry/phase/grant/drain checks followed by URI-based delete without an independent file-incarnation witness. The prior single-item source freeze remains immutable. This next slice corrects that same adapter for both single and batch flows: a present target is not automatically deleted when URI/token/grant are the only ownership evidence; independently confirmed absence may still produce REMOVED. No unrelated file is adopted or deleted by a renewed picker. Do not claim native identity checks exist.

To avoid trapping the scalar journal after a safely drained but retained output, single-copy gains explicit `OUTPUT_RETAINED`: authenticated current action, known pre-final CAS, no unresolved IO, same fixed-store exact-target validation, immutable terminal non-success receipt, and permanent target authority retirement. It is never available for PUBLISH_INTENT or an unknown final decision. It records possible incomplete ordinary output and retained Vault original, never “cleaned” or “copied.” New operations are allowed after that terminal receipt; the retained item is not automatically retried. Batch uses its existing CANCELLED + UNRESOLVED_RETAINED row mapping. Wire v2 supports this one new single outcome as well as batches; unchanged legacy single records remain v1. Tests must cover single and batch same-URI replacement/fresh-regrant cases without claiming device reproduction.
