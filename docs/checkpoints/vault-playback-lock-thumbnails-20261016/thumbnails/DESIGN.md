# Vault private static thumbnails: minimum connected slice

Status: design only, 2026-10-16. No baseline edits, implementation, build, device access, credentials, real media, publication, or old-probe execution. Production remains `AndroidVaultRuntimeEntry.ENABLED = false`. Native decode/device/security acceptance: **NOT_RUN**.

## 1. Decision and source requirements

Use the existing platform MediaMetadataRetriever single-frame operation, fed by a small Android MediaDataSource adapter over the existing Vault controlled-read reservation. Retain only current protected presentation frames in memory. No plaintext file, FD/URI export, public loader, ordinary/shared cache, new dependency, player-per-row, parser, scheduler, authentication owner, store owner, or crypto format.

This implements a finite static cover for genuinely visible revealed Vault rows. It does not add a gallery, prefetch, animation, seek-strip, background generation, stored thumbnails, new media profiles, or production enablement. Null/error/over-budget output remains a localized placeholder.

Requirements read:
- Original PR-18/product §8: protected sensitive thumbnails; clear private views on lock; free Vault.
- TR-12/technical §8.3: controlled streaming, revoke session/clear plaintext caches, no thumbnail/index plaintext storage. This narrower slice never writes thumbnail bytes at all.
- Original acceptance T-L05/T-L06/T-P07: background/recent-task/restart protection, ciphertext corruption rejection, no ordinary cache/plaintext leakage.
- Original UI 01 §4.5/§8; 03 UI-R11/§6; 05 §10; 08 framework-policy §§2/6: reuse existing media reader/thumbnail facilities, distinct private identity/lifetime, visible-sized decoding, offscreen cancellation, no ordinary disk/shared URL-key cache or second engine. Original tester T-07/T-23/T-24 and traceability PPT19 remain separate real-Android gates. Relevant original UI sections were read from the parent-verified nine-file shared handoff; package hashes are in BASELINE_HASHES.json.

## 2. Actual reuse, including the missing seams

1. `AndroidLibraryThumbnails.kt` already calls `MediaMetadataRetriever.getScaledFrameAtTime(0L, OPTION_CLOSEST_SYNC, 256, 144, BitmapParams(ARGB_8888))`, validates dimensions/allocation, and returns an opaque `AndroidThumbnailFrame`. Extract that exact primitive and its single process native lane for both callers. Keep the same `OrdinaryMediaNativeResources` gate; a stalled ordinary job also blocks a Vault decode and vice versa. Do not construct another executor or reuse `AndroidLibraryThumbnails.currentSession`.
2. Ordinary input is currently a private, FD-only backend over `MediaReadRef`. It cannot safely receive ciphertext or a fabricated ordinary reference. Add only `MediaDataSource` input adaptation. Platform API23 supports `setDataSource(MediaDataSource)` and API30 supports the exact scaled-frame/BitmapParams overload; both precede minSdk31. Pinned Android36 signatures are captured in PINNED_ANDROID36_APIS.txt. [Android API](https://developer.android.com/reference/android/media/MediaMetadataRetriever), [MediaDataSource semantics](https://developer.android.com/reference/android/media/MediaDataSource).
3. `VaultRuntime.playbackSession` already authenticates the exact revealed ref, current readLease/root/auth epoch/presentation epoch/catalog revision and host token under the sole runtime gate. Extend the same admission and the existing `VaultPlaybackRuntime.Entry` reservation with internal purpose PLAYBACK or THUMBNAIL. Reuse its file acquisition, `readPort`, `publicationGate`, in-flight reads/permits and actual reader/file retirement. THUMBNAIL never creates a Player, Surface, audio output, Media3 parser or playback UI status. Do not clone another read owner.
4. Reuse `BoundedThumbnailSession` as the bounded request/result algorithm, with a narrowly typed generic key/item adapter instead of converting private refs to ordinary `MediaItem`. Its identity is not authority. A private instance belongs to the existing application binding/host lifetime; it is not an independently constructible Vault or global image cache. Preserve ordinary compatibility, cancellation, exact retirement and tests.
5. Integration seam: that session currently assumes synchronous `decode`; the existing Vault reservation prepares and retires asynchronously. Add a callback-completion seam to this same algorithm, retaining the ordinary synchronous wrapper. One session job remains active until the actual controlled-read/native cleanup and result handoff finish. No `Future.get`, latch, Main wait, worker replacement, or second scheduler. Reuse the existing Vault work executor for setup/read retirement, shared thumbnail native lane for MMR, existing UI executor for handoff, and existing VaultWakeScheduler for the private watchdog. Never execute MMR on Main or the serial Vault command lane.
6. Async completion is at most once for the exact request token, with separate once-only result-claim, frame-transfer and job-settle facts. A duplicate callback carrying the same already-adopted frame is a no-op, never a second close. Only a never-adopted orphan result may retire its own frame; no late callback may close or finish a replacement request. Register admission/acquisition and result handoff before invoking external callbacks. Process admission remains occupied over prepare → native decode → reader/file retirement → Main consumption/discard. Rejection, execute-then-throw, callback exception, or an uncertain post cannot first release the process gate or drop an owned frame. Preserve the ordinary synchronous path's ordering and behavior.

## 3. Minimal lifetime contract

### Admission and display
- Existing protected Host creates a process-local request identity from its current claim/atomic action epoch and cover generation; exact `VaultMediaReadRef` includes object generation/catalog revision. The runtime additionally binds its current readLease/root/auth epoch. Fields alone never reconstruct authority. UI sees only bounded technical state and an opaque draw handle, never Bitmap, ImageBitmap, reader, key, path, URI, or serialized request.
- The current Vault page is `Column.verticalScroll` plus `items.forEach`, so composition is not visibility. Use the already admitted Foundation lazy-list pattern and `layoutInfo.visibleItemsInfo`; intersect actual visible row identities with the exact revealed catalog. Keep all controls as list items and preserve selection/lock/export behavior. Never use `LaunchedEffect`/composition of every row as permission to decode.
- Reuse the ordinary screen's explicit “load visible thumbnails / stop” interaction, protected by current Host action admission. Starting/stopping is presentation work only. Lock/route/foreground/host/capture loss clears intent; there is no automatic restart on return. More than 16 visible rows gets placeholders beyond the first 16, in stable viewport order.
- Only one controlled read/native decode may be active across Vault playback and thumbnail work. Reject/placeholder while playback, media move/copy/reconciliation, authentication/recovery, missing visibility, invalid host, current cleanup, or owner drains make admission unavailable. Cancel/retire thumbnail work before other user-selected Vault operations can acquire the same reservation. Do not silently queue playback/export behind unknown cleanup.
- Deliver a successful frame only after the exact native decode and reader/file resources have actually retired, while the same auth/catalog/request/host/visibility identities remain current. The display token is distinct from the per-operation read token that the existing Entry revokes on retirement, but remains bound to the original Host/auth/catalog presentation. Healthy read retirement cannot revoke that display token, and a live display token cannot revive a retired reader. A transferred frame remains registered to the same binding/host after the read reservation is released; otherwise the next visible row could never decode.

### MediaDataSource bridge
- `getSize` and every `readAt`, including zero-length/EOF, first check exact current authority under the existing gate. Source size is the existing authenticated extent (1..2 GiB), not a native estimate; no new format admission or metadata parser.
- Validate negative offsets/lengths/positions and overflow with subtraction, not `position + requested`. `size == 0` returns 0 only after current/range checks; at/beyond authenticated EOF returns -1 only for a live, valid request. Revocation, timeout, budget, corruption and authentication failure are fixed-code IOException/unavailable, never normal EOF.
- The platform may request more than the existing 64 KiB buffer. Return a positive short read capped at `min(requested, remaining extent, 64 KiB, remaining operation budget)`. No allocation or read loop sized by untrusted callback length. Existing controlled reader performs authenticated scratch-to-destination publication and clears its scratch; do not insert a second plaintext accumulator.
- Account both read and getSize callbacks under the runtime gate before invoking capabilities; one admitted byte-read at a time. All accepted callbacks remain counted until actual return. Bound one thumbnail to 3 seconds admission lifetime, 8 MiB cumulative returned plaintext and 512 total callbacks, including repeated seeks/zero-length/getSize. These conservative thumbnail-specific caps add restrictions only; budget exhaustion yields a placeholder and ordinary read cleanup. They do not claim 8 MiB of ciphertext IO because Tink has segment read amplification.
- `MediaDataSource.close` is an idempotent transport-close fact only. It revokes further callbacks and never closes the shared reader/file directly, proves MMR release, or acknowledges whole Vault cleanup. Native `release()` may itself call it and may throw even on older APIs.

### Revocation and retirement
- Register the exact native acquisition obligation and strong owner reference before MMR construction/setup/decode, then register result and Main handoff before posting. A constructor/setup/release failure, lost/ambiguous executor handoff, or stalled native call remains retained UNKNOWN. No generic `finally`, timeout, post acceptance, Compose disposal, nulling state, or cancellation flag is a release receipt.
- Lock/route exit/background/device-lock/capture conflict/host replacement invalidates the request and display tokens first, installs the existing secure-root barrier, clears pending visible requests/semantics and cancels active work. Do not wait for native return before hiding private output. Recheck exact token after decode, before/inside Main publication and at every draw; a late frame is closed/discarded, never published.
- Keep native completion, accepted callbacks, reader close, ciphertext anchor close, Main handoff, app-owned frame close and exact protected-host visual retirement as distinct facts. Reader/file may be revoked and independently retired after admitted reads/permits actually return, even if native release is unknown. Do not make safe read cleanup wait forever for a failed native decoder.
- On healthy completion, MMR release must actually return; transport/callback counts must drain; reader `closeAndObserve` and then file `closeAndObserve` must report RELEASED. The asynchronous session completes only after these facts and handoff ownership settle. A returned Bitmap alone is never success.
- Reuse `AndroidThumbnailFrame` safe post-close no-image drawing. Add the private exact-token draw guard without exposing pixels. A never-drawn frame can be recycled. After Canvas submission, existing close drops the application reference without unsafe recycle; it does **not** prove native/GPU pixels were zeroed. Global cleanup also requires the existing exact generation cover-frame/root-detach evidence. Do not invent a GPU-erasure receipt or require impossible GPU zeroization to report only application-reference retirement.
- Avoid a cover-acknowledgement cycle: use the Host's already-observed `coveredGeneration == generation` or actual root-detach fact to retire display obligations, then evaluate `hostResourcesRetired`, then deliver the aggregate cover receipt. Do not make frame retirement wait on that aggregate receipt, which itself waits for host resources. Normal offscreen confirmed frame close may return its app-owned bitmap slot/bytes while the protected Host stays valid; retain only the bounded exact presentation-retirement marker until global cover, never a hidden offscreen bitmap or a claimed GPU release. Unknown frame close retains the frame and budget.
- Include all thumbnail job/callback/handoff/frame/host obligations in `VaultRuntime.tryAcknowledgeCleanup`, `hostCleanupComplete`, Host `hostResourcesRetired`/`ordinaryReleaseAllowed` and presentation attachment arbitration. The absence of `playback.current` alone is insufficient. Unknown work retains the original owner and blocks new private readers/native work; a new Activity/session cannot reset that fence.

## 4. Fixed budgets and failure behavior

Reuse ThumbnailLimits: one static 256×144 maximum ARGB_8888 frame, 36,864 pixels, <=147,456 allocation bytes; <=16 pending visible identities; <=16 private retained/pending/retiring frames in total and <=2,359,296 private app-owned frame bytes. Reserve one frame slot/147,456 bytes **before** decoding, so the in-flight result is included rather than creating a seventeenth frame. Count across old hosts, retiring private session and queued Main handoffs. Never admit a replacement on unknown release. Existing native lane remains one thread with its existing one-slot executor queue, and the process gate keeps at most one actual native owner. Ordinary storage remains separate with its existing bound; the private 2.25 MiB limit is not a claim that all app image domains together use only 2.25 MiB.

Use the existing bounded-session map only as current visible presentation storage: pass the bounded visible set as its page so leaving the viewport retires the frame; do not retain an offscreen LRU or prefetch. Each exact ref gets at most **one started native attempt per reveal**. Record that fact immediately before the first MMR acquisition/setup invocation under the admitted job. Queued work cancelled before native start, or an admission rejected as busy, consumes no native attempt and may rejoin when visible. A real preparation/authentication failure is terminal-unavailable for that reveal, not an invitation to retry on recomposition. Once native acquisition starts, cancellation, failure or UNKNOWN consumes the attempt and stop/start/scroll cannot reset it. This first slice has no retry command; a fresh reveal follows the existing cover/cleanup path. The existing authenticated catalog wire bound is at most floor((65,536 − 33) / 220) = 297 entries (actual valid catalog may be smaller); attempted/terminal-identity accounting must reject more than 297, with no changes to that wire format. A viewport update may cancel work as the current bounded session already does; this is conservative and must never retry indefinitely while scrolling.

The three-second watchdog removes authority and stops further submissions; it cannot kill a native MMR call. Keep the existing sticky native gate behavior. App-owned bitmap/queue/read limits and one-native-call concurrency are enforceable. Total platform decoder/renderer/GPU allocation, hard native execution time and pixel erasure are **not** established by these counters. Actual Android tests must characterize them before a production/security claim.

Generic localized labels only for loading/unavailable/cleanup-unconfirmed. Do not put the item name in thumbnail contentDescription, error text, cache key string, log, SavedState or test report. No private icon/image/title survives cover into the semantics tree. Continue existing SkinKit visual tokens, locale resources and noninteractive aspect-ratio/placeholder component.

## 5. Touch map and implementation order

1. Shared thumbnail facilities: `app/.../library/thumbnail/AndroidLibraryThumbnails.kt` (extract existing native lane/MMR primitive/opaque frame, ordinary behavior preserved), `OrdinaryMediaNativeResources.kt` (reuse process gate, no new singleton), `library/.../thumbnail/BoundedThumbnailSession.kt` (typed identity + async completion seam; existing wrappers/tests remain). Avoid changing the ordinary source/catalog fence.
2. Existing Vault owner: `VaultRuntime.kt`, `VaultPlaybackRuntime.kt`, `VaultPlaybackContracts.kt`, `AndroidVaultRuntimeEntry.kt`. Add internal THUMBNAIL purpose, shared admission, finite request reservation, exact read/native/result retirement, cleanup aggregation and injected shared decoder. Production remains false. `VaultControlledMediaReader`, authentication/store/file formats should require no semantic change.
3. Thin Android bridge: new `app/.../vault/thumbnail/AndroidVaultThumbnailDataSource.kt` for MediaDataSource adaptation and small adapter to shared MMR primitive. No new renderer/player/cache/network/permission component.
4. Existing protected presentation: `AndroidVaultPresentationOwner.kt`, `VaultProtectedHost.kt`, `VaultRuntimeUi.kt` plus a small private thumbnail composable, localized EN/zh-CN labels. Host holds private session/opaque frames, exact-generation cover receipts and unknown retirement; UI never supplies authority. Root warning/cover behavior is reused rather than replaced.
5. Deterministic fake-port tests before source integration; independent storage and platform review; then central build-owner focused/full regression/lint. No build in this task. New APIs should remain internal and default-disabled test injection must not become a production unlock switch.
