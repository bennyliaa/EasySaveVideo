# M6-B proposed implementation sequence and capture-data boundary

M6-A supplies ordinary-media post-processing; it does not implement capture-time region selection or recording segment orchestration. This plan introduces no feature activation or additional permission request.

1. **Freeze the capture recipe and disclosure.** Define a typed region intent carrying normalized bounds, actual capture dimensions, display rotation, insets and transform version. Implement phone/tablet selection, drag/edge/corner controls, full/reset/confirm/cancel and an exact selected-versus-captured explanation before recording. Keep the existing RECORD_SAVE + REGION_RECORDING / SEGMENT_RECORDING gates and free Stop/Cancel. Coordinate with current M4 consent, one-use grant and foreground-service ownership.
2. **Implement recoverable recording segment ownership.** Add ordered, independently verified segment records tied to one explicit session, codec/audio/orientation configuration and actual effective timestamps. Define pause/resume and system-stop boundaries without automatically reusing a revoked projection grant or violating platform one-session display constraints. Retain valid segments on interruption; do not label a group of loose files a completed merged video. Existing M4 consent and raw-recording evidence must remain valid and separately tested.
3. **Implement and verify the capture crop route.** Prefer cropping the selected pixels before encoding so no full-screen recording is written to disk. Platform projection may still supply a full capture surface transiently: describe that accurately rather than claiming the OS captures only an arbitrary rectangle. Validate actual API31+ surface ownership/rotation and GPU teardown before enabling this route. Rotation/configuration changes must safely stop or start an explicit new compatible segment, never silently capture a different area.
4. **Integrate ordered merge and post-crop with M6-A.** Feed only independently verified, current owned segment capabilities into typed edit jobs; preserve segment order, actual timestamps and provenance. Atomically publish one new verified result. Offer optional second crop and compression, with the current profile/quality limits and source retention rules. Add end-to-end cancel/restart, consent revocation, orientation, AAC priming and mixed-configuration fault tests, then independent source review and the separately authorized device matrix.

## If a full-screen-then-crop fallback is considered

It must be a visibly different capture-data route, disclosed and explicitly selected before the system capture starts. The user must be told that temporary full-screen video, including content outside their selection, is recorded in app-private storage while processing. A selected rectangle alone must never be presented as consent for undisclosed full-screen files.

Temporary full-screen artifacts must have their own typed private ownership, time/byte/space limits and crash-safe cleanup. They must not enter the ordinary catalog, preview/thumbnails, export/share or public storage as a successful region result. Region processing is mandatory for success. Crop failure, cancellation, unsupported parameters or interruption cannot fall back automatically to publishing the full-screen original. If a future recovery option exposes or retains that full-screen recording, it requires a separately explicit user choice and accurate labeling; it is not a successful selected-region result.

Successful cropped publication may authorize cleanup only after all native readers/writers have actually released. Cleanup failure stays visible and bounded; a timeout is not closure. Restart recovery must retain enough ownership metadata to identify and clean the exact temporary artifact, without directory scans or speculative deletion. No Vault dependency or protection claim may be used to justify temporary plaintext retention.

## Gates

Before implementation activation, settle the exact platform capture route, temporary-data disclosure and codec/profile subset. The current authorization permits code and host validation only: actual MediaProjection permission flows, recording, device/GPU behavior, APK/AAB and publishing remain NOT_RUN unless separately authorized. M6-B is a subsequent checkpoint, not a hidden part of M6-A acceptance.
