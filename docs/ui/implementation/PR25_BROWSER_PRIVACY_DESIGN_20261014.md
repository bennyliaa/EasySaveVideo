# ESV PR-25: Incognito and site-permission reconciliation

Date: 2026-10-14. This is a read-only architecture review, not implementation or acceptance. No Gradle, dependency download, device operation, permission grant, or source-tree modification was performed for this review.

## 1. Recommendation

Do not expose an Incognito toggle on the current `SystemBrowserHost`. Its logical tab flag does not isolate the actual WebView storage, and the Save adapter reads the default cookie jar.

There are two legitimate architectures:

1. **Keep the current admitted graph:** a dedicated, non-exported private-browser Activity/process with a unique platform WebView data-directory suffix. This provides real normal/private storage separation without a new Android permission or library. It requires process ownership, exit/crash cleanup, and an explicit cross-process Save/Record boundary. Treat complete cleanup as an engineering acceptance gate, not as a property of the suffix API.
2. **Review a new official AndroidX WebKit dependency:** use a named private profile, feature-gated on both multi-profile support and complete browsing-data deletion. This is the smaller fit for the existing single-Activity/tab UI, but cannot enter the frozen 90-artifact graph without exact artifact/transitive/license admission. A profile is not automatically memory-only, and destroying its WebViews is not deletion.

Prefer reviewing option 2 for the integrated-tab product. If dependencies must remain frozen, implement option 1 as a deliberate architecture slice, not a shortcut inside the existing host. Do not ship either as “no traces” or “never touches disk.” No reviewed evidence establishes an ephemeral, all-memory WebView facility here.

Independent useful work is available now; see section 7. It must not be counted as completion of Incognito or camera/microphone/location grants.

## 3. Isolation architecture and cleanup

### Platform-only process route

The supported primitive is `WebView.setDataDirectorySuffix`, available from API28. It must run before any WebView creation **or other android.webkit call in that process**. The suffix separates both WebView data and cache locations; it is process-wide, not a switch on an individual View. Keep normal browsing on its current default directory; private browsing uses a different, non-exported `:private` process. An Android process sharing the app UID is lifecycle/data separation, not an additional security sandbox against ESV's own code. [WebView API](https://developer.android.com/reference/android/webkit/WebView#setDataDirectorySuffix(java.lang.String)), [Activity process declaration](https://developer.android.com/guide/topics/manifest/activity-element#proc)

Proposed minimum lifecycle:

- Give each private session an opaque random generation, never a URL-derived suffix. All tabs within that session may share its private login state; normal tabs cannot. Never change an existing tab's partition by toggling a Boolean.
- Construct a private composition root. Do not instantiate ordinary history, bookmark writers, ordinary Discovery persistence, normal session restoration, or the main process's duplicate Save/storage owners in this process.
- Use a narrow process-local/private Binder interface for explicit actions. Ordinary navigation Intents, saved task stacks, SavedState and persistent navigation arguments must contain no private address, title, query, cookies or signed media URL.
- On final-private-tab close or explicit exit, synchronously revoke the session generation, stop new work, deny pending page requests, cancel inspections and session-bound credential access, detach/destroy every private View and discard in-memory histories/drafts. Complete child shutdown before deleting its owned storage. Never kill the normal/recording process to clear private browsing.
- A suffix does not provide a public “delete this whole directory and await completion” API. Framework CookieManager/WebStorage/cache clearing alone must not be asserted to remove every Chromium storage class. If implementing app-owned directory cleanup, first establish exact ownership of **both data and cache locations**, no live process/writers, path/symlink boundaries and provider-version behavior; guessed recursive deletion of Chromium internals is not an accepted implementation. Failure must quarantine the old generation, avoid reuse, and remain visible as incomplete cleanup.
- Retain only bounded opaque cleanup markers, not browsing data. Retry cleanup at cold startup before restoring or reusing any private partition; never revive private pages after process death. Immediate cleanup cannot be promised after a system kill: Android need not invoke `onDestroy`. [Process lifecycle](https://developer.android.com/guide/components/activities/process-lifecycle)

**Status:** supported isolation primitive; complete cleanup and integrated product behavior are still unimplemented/unverified. No new dependency or OS permission is intrinsically required. The architecture/validation work is an engineering choice; unsupported privacy claims are not an acceptable fallback.

### Reviewed AndroidX profile route

`Profile` maintains its own data and exposes profile-specific cookie, storage, geolocation and service-worker managers. `WebViewCompat.setProfile` must be called before using the View, including navigation/evaluation; profile assignment cannot be changed later. Use a random private-session profile, selected before settings/history restoration. Every helper, especially Save's cookie capture, must use that exact profile. [Profile](https://developer.android.com/reference/androidx/webkit/Profile), [setProfile](https://developer.android.com/reference/androidx/webkit/WebViewCompat#setProfile(android.webkit.WebView,java.lang.String))

Do not design exit around `ProfileStore.deleteProfile` alone: it rejects a loaded profile/live Views, cannot delete the default profile, and can return before all disk deletion finishes. `WebStorageCompat.deleteBrowsingData` (API added in WebKit 1.13.0) has a completion callback and covers network cache, cookies and JS-readable storage. Deletion is not atomic with concurrent writes: fence creation/navigation, release Views, stop app-managed work and validate service-worker behavior before reporting completion. Independently clear app-owned permission grants and session state. Never reuse a profile whose cleanup is uncertain. Loaded-profile retirement and leftover profile metadata deletion need a tested cold-start path; do not call `getProfile` on a retired profile before trying to delete it. [ProfileStore](https://developer.android.com/reference/androidx/webkit/ProfileStore#deleteProfile(java.lang.String)), [WebStorageCompat](https://developer.android.com/reference/androidx/webkit/WebStorageCompat)

Require `WebViewFeature.isFeatureSupported(MULTI_PROFILE)` **and** `DELETE_BROWSING_DATA` at runtime; SDK level alone is insufficient. Unsupported providers must not fall back to the normal profile under an Incognito label. Multi-profile starts in 1.9.0; complete deletion starts in 1.13.0. The first concrete candidate for a bounded admission review is **`androidx.webkit:webkit:1.17.1`**, the current official stable release (2026-09-23), verified against the live release table on 2026-10-14. Its release note removes Kotlin from the library to address kotlinc compatibility. The older stable **1.15.0** (2025-12-17, minSdk23) also contains the required API generations, but is not the current stable release; it is a fallback candidate only if the exact modern artifact metadata/graph gives a concrete incompatibility, not an assumed downgrade. Version 1.16.0 raised the library minimum to API24, below ESV min31. Actual 1.17.1 AAR metadata/compileSdk/Kotlin requirements and the full resolved transitive changes still need inspection; final compatibility is not established by these release notes alone. Audit official bytes/licenses/full graph, then update lockfiles/admission/notices under the existing gate. This is a review candidate only; no artifact was downloaded or admitted. [Feature contract](https://developer.android.com/reference/androidx/webkit/WebViewFeature), [release notes](https://developer.android.com/jetpack/androidx/releases/webkit#1.17.1)

## 4. Required data and command boundaries

**Identity:** introduce a platform-neutral normal/private `BrowserPartitionRef` or equivalent session-owned capability. Bind it to tab, navigation epoch, document/View identity, permission claims, inspection selections and credential leases. It must not be inferred from the currently selected UI tab after asynchronous work. Current `SaveInspectionPage` and `PageSaveSelection` carry no partition identity.

**Browsing/discovery:** private URLs/titles/queries/Seen/Progress/permission decisions stay in that session's memory; no normal checkpoints or restored page loads. Address-bar drafts currently use `remember`, which is helpful; preserve that. Same-process RAM LRU history is acceptable only inside the private owner and must vanish at exit. Private video search must pass to a genuinely private Discovery owner; do not copy its query into the current ordinary controller. Apply same partition fencing to thumbnails, cached result pages, origins and stale callbacks.

**Explicit Save:** preserve the ordinary browser product's explicit select/confirm/destination flow. Incognito is not Vault. Before the user deliberately saves, explain that the chosen file and its task record survive closing private browsing. No implicit Save or Seen event is authorized by opening a page. `SystemBrowserHost.kt:305–327` already excludes private Discovery-origin tracking; `AuthenticationOriginPolicy.kt:73–100` excludes private authentication-return handles. Preserve these exclusions unless replaced by a session-scoped private implementation.

`AndroidSaveRuntime.kt:887–893` currently reads the **global** cookie jar after a same-origin check. Replace this with a partition-bound credential port; never query/copy all cookies. `app/src/main/java/.../RequestContextLeaseStore.kt:12–59` already uses memory-only, 60-second default leases, exact selected resource and first-hop-only headers, but has only individual/all revocation, no private-session owner. Add owner-generation revocation and an outer active-request fence: removal from the map cannot retract headers already copied to an in-flight network request. Ending a private session must cancel or stop further credential use; already published user-saved media is not erased automatically. Do not silently fall back to normal cookies or renew private credentials after exit.

`save/.../SaveModels.kt:41–44` and `app/.../storage/SaveRecordCodec.kt:14–28` persist only origin plus source hash, not signed URL/headers. That **still retains source-origin metadata** in ordinary task history. It must be included in the deliberate-save disclosure, or require a separately agreed privacy-preserving Save schema. Do not describe current journaling as leaving no metadata. Finalized files/task recovery remain governed by the existing explicit media lifecycle.

**Recording:** the current browser Record click only navigates to the Record route (`MainActivity.kt:676`); it carries no private capture intent or disclosure. `RecordingConsentController.kt:23–114` correctly keeps projection authorization outside SavedState. Preserve per-session MediaProjection consent and the single media owner. RECORD_AUDIO is currently needed for playback capture; it is not a website-microphone consent. [Playback capture](https://developer.android.com/media/platform/av-capture)

**Recent tasks, screenshots and outbound actions:** T-P07 requires separate verification. `FLAG_SECURE` prevents screenshot/non-secure capture and therefore conflicts with promising private-page recording. API33+ can suppress recent-task snapshots separately; that API does not exist on API31/32. Choose and test an explicit user-initiated capture exception (including risk disclosure and restoring protection), or honestly make private-page recording unavailable in the initial slice. Do not silently drop the required privacy boundary or return a black recording as success. Explicit copy/share/external-browser/file-picker actions can transfer private data out; show the destination/scope and require their existing user action. Keep private View autofill/content-capture/snapshot surfaces out of ordinary persistence. [FLAG_SECURE](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#FLAG_SECURE), [recents API](https://developer.android.com/reference/android/app/Activity#setRecentsScreenshotEnabled(boolean))

## 5. Site-permission manager

Keep three independent facts: app capability admitted/implemented; OS permission currently granted; website decision for this exact origin and private/normal partition. None implies the other two.

- Origin key = validated scheme + canonical host + effective port, never path/title/suffix-match/eTLD+1. Preserve existing controlled URL parsing and test default ports, IDN/punycode, IPv6, malformed/opaque origins, misleading subdomains and HTTP/HTTPS separation. A conservative first implementation allows requests only from the active HTTPS main-document origin; deny cross-origin frames until attribution/delegation is genuinely supported.
- Normal persistent settings may contain `DEFAULT` and explicit `BLOCK` entries. `DEFAULT` means evaluate current app/OS/user policy; it does not mean “allowed.” Reset deletes the website preference; it does not grant Android permission. Only persist origins the user deliberately configures; do not turn every denied request into durable browsing history.
- Private decisions are memory-only for the session. Do not write them to the normal preference store. Normal grants must not silently carry into a private session; normal safety blocks can be read as restrictive defaults without copying private origins out.
- A real grant flow must show the requesting origin and exact resource, support Cancel/Deny, correlate the result with partition/tab/epoch/document/View/request identity, check OS permission immediately before grant, and retire on cancel, navigation, tab switch, background, renderer loss, route leave or exit. Handle `onPermissionRequestCanceled` and geolocation hide callbacks. Late OS responses never grant a replacement page; never automatically relaunch prompts after restoration.
- Classify `RESOURCE_AUDIO_CAPTURE`, `RESOURCE_VIDEO_CAPTURE`, MIDI, protected-media identifiers and unknown future resources separately. Unknown/unimplemented resources and mixed unsupported requests are denied. Never pass `request.resources` wholesale into `grant`. A grant response names only explicitly implemented and user-approved constants. Both grant/deny run on the UI thread. [PermissionRequest](https://developer.android.com/reference/android/webkit/PermissionRequest)
- Camera needs a reviewed CAMERA declaration and runtime request. Location needs the exact approved coarse/fine scope and runtime flow; no background location is needed or proposed. Geolocation must also be enabled on the relevant View and use profile-correct state. Current `setGeolocationEnabled(false)` means a location-prompt manager alone would not make it usable. For private grants use non-retained callbacks/app-memory policy. [WebChromeClient geolocation](https://developer.android.com/reference/android/webkit/WebChromeClient#onGeolocationPermissionsShowPrompt(java.lang.String,android.webkit.GeolocationPermissions.Callback)), [runtime permissions](https://developer.android.com/training/permissions/requesting)
- Website microphone technically can use the existing RECORD_AUDIO manifest declaration, but changes the permission's functional purpose. It needs an explicit scope decision plus website-specific consent, even if the OS was already authorized for internal-audio recording. Do not use recording authorization as that consent. No camera/microphone/location grant is approved or performed by this design review.
- Downloads/external navigation remain separate user actions. A site setting cannot authorize arbitrary executable schemes, native Intents, bulk downloads or hidden uploads. Keep current manual media-selection and file-picker recipient checks.

**Avoid misleading UI:** while all sensitive web capabilities remain unimplemented, show their actual unavailable reason; do not offer a functioning-looking Allow button. Adding a stored BLOCK/DEFAULT selector when both still deny everything is policy groundwork, not a completed permission manager or substantial new capability.

## 6. Exact gates and decisions

**Engineering choices within the original requirement:** partition identities, process versus profile architecture, private in-memory stores, stale-result fences, cleanup state machine, origin normalization, generation-bound leases and tests. These do not themselves require new Android permissions. This assignment authorizes analysis only; it did not authorize implementation here.

**Review gate:** choosing AndroidX WebKit requires exact artifact and transitive/license review/admission before downloads/integration under the project's current constraint; never weaken equality to allow an unmatched graph. Camera/location declarations and website microphone use require an explicit purpose/scope decision before enabling or testing access. Actual runtime OS grants/camera/microphone/location access are not part of routine build/emulator authorization.

**User/product decisions only where necessary:** accepting private-page capture's privacy exception on API31/32; any reduction of the original exit-cleanup promise; allowing retained task provenance beyond the disclosed deliberate Save action. Do not ask the user to choose low-level class names or routine engineering mechanics. A “no traces on disk ever” requirement would need a different, separately reviewed engine/storage solution; neither proposal supplies that guarantee.

## 7. Genuine independent next slices

1. **Central ordinary-cookie clearing:** `ui/shell/PrivacySettingsDetail.kt:21–54` currently exposes history/cache only. Real cookie clearing exists only in `ui/BrowserScreen.kt:429–434,467` through `SystemBrowserHost.kt:399–405`. Reuse the real operation in central Privacy settings with shared one-shot confirmation, explicit sign-out warning, async result/route ownership and repeat-click fencing. This completes an original settings gap without new dependencies/permissions. It is ordinary cookie clearing, not site-storage deletion or Incognito. Test callback loss/false result, navigation away, recreation, concurrent page cookie writes and expired confirmations; do not call it irreversible secure erasure.
2. **Truthful request classification and stale-notice fencing:** `SystemBrowserHost.kt:714–723` denies every WebView permission but labels every `PermissionRequest` as camera/microphone, including MIDI/protected-media/unknown requests; it updates UI without checking whether the Entry/document is still current. Implement exact resource classification and lifecycle-safe notices while keeping fail-closed behavior. This is an actual correctness fix, not a new grant feature.
3. **Private-boundary foundation tests:** introduce partition-aware command/lease/cleanup contracts, prove no normal writer receives a private value and test late callback/session revocation, without exposing an Incognito entry until a real adapter passes its isolation/cleanup tests. This advances PR-25 engineering but is not user-facing completion.

## 8. Acceptance required before claiming PR-25 complete

- On supported API31 and a current API36 provider: normal/private same-site cookie/login, local/session storage, IndexedDB, service worker/cache and permissions cannot cross; ordinary state remains intact after private exit.
- Final-tab exit, close-all, renderer crash, rotation/recreation, app/process kill, force-stop/relaunch, offline cleanup, timeout/failure and repeated private sessions never restore prior private state or reuse unverified storage. Test UI/LRU recreation and same-URL navigation callbacks.
- Inspect ordinary session/history/Seen/Progress/preferences/task records, SavedState, recent-task images, backups, notifications and release logs with owned synthetic canaries, not real accounts/secrets. Task metadata is present only after the explicitly disclosed Save/Record action.
- Save credential capture is exact-partition and exact-document; closed-session and stale requests cannot renew or publish using old credentials; redirect rules remain unchanged. Normal saves survive private cleanup without receiving private credentials.
- Permission denial, OS revocation/one-time expiry, mixed/unknown resources, same-origin versus cross-origin frames, tab switches, repeated prompts and late callbacks are correct. No unsupported Allow path. Real camera/audio/permission behavior requires separately authorized runtime acceptance, not JVM inference.
- No new dependency, manifest permission or device action occurred in this review. All Android runtime/security acceptance above is NOT_RUN.
