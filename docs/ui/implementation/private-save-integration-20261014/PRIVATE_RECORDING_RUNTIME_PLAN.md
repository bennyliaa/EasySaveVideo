# Private recording ③: minimum Android/runtime integration

2026-10-14. Read-only source investigation; no source edits, Gradle, remote, or device operations. This is a proposed integration contract, not platform acceptance. Source inspected: `/workspace/shared/esv-cloud-handoff-20fddc9/source`. Existing pure `PrivateCaptureExceptionPolicy` is reused. User intent remains private Save ①②③, preserved committed media, and denied website camera/microphone/location.

## Decision summary

- Keep the current BROWSER route and exact selected WebView. Add a private capture presentation in that same ownership tree. Do not navigate to the current RECORD route: its ordinary screen hides the selected browser surface.
- First implement BASIC plus its chosen silent/internal-playback-audio mode. This completes only the first recording submode; REGION/authorized-frame preview remain explicitly unwired until the existing segment owner participates. Do not advertise all recording subfeatures as complete or remove ③ from the minimum-API requirement.
- API33+ supplies a public independent recents-screenshot suppression API. API31/32 do not acquire equivalent evidence merely by task exclusion. Keep a temporary capability gate while the parent resolves the explicit legacy-risk choice below; no permanent product deletion is proposed.
- The first code slice can be the real Android root/window guard alone. It must not flip `PrivateBrowserIntegration.ready()` or issue capture evidence before the Record bridge and platform gates are complete.

## Frozen first slice: real window and structure protection

Minimum new files:
1. `app/.../browser/privacy/PrivateContentRoot.kt`: an app-owned `FrameLayout`, structure suppression, direct opaque cover, and testable state.
2. `app/.../browser/privacy/PrivateWindowGuard.kt`: Activity-owned registration of exact Window/Decor/content-root identities, synchronous protection requests, capability reporting, and no media ownership.

### PrivateContentRoot contract

- Place all app content capable of showing private data below this real Android parent. Private protection is an explicit main-thread state; do not infer it from a Compose semantics node.
- While private/transition/capture suppression is enabled, override `dispatchProvideAutofillStructure(structure, flags)` without calling `super`: set this root's `AutofillId`, `AUTOFILL_TYPE_NONE`, and zero children. Populate no text, hints, URL, HTML information, content description, or virtual descendants. Apply this for `AUTOFILL_FLAG_INCLUDE_NOT_IMPORTANT_VIEWS` too. Outside the protected interval, delegate unchanged to `super`.
- Also suppress the private hierarchy in `dispatchProvideStructure` (an empty own node/zero children, no `super`) for Assist structure traversal. This is structured-data containment, not a promise to prevent every system screenshot or accessibility observation.
- Install `IMPORTANT_FOR_AUTOFILL_NO_EXCLUDE_DESCENDANTS` and `IMPORTANT_FOR_CONTENT_CAPTURE_NO_EXCLUDE_DESCENDANTS` on the real DecorView, `android.R.id.content` parent and app-owned root; store/restore prior ordinary values only after safe ordinary presentation. Check actual values on these real Views. Do not require AndroidComposeView to honor the setter: the exact admitted Compose 1.8.3 binary was independently checked in `PRIVATE_UI_REVIEW.md` and its autofill getter returns YES.
- The opaque cover must be an actual native drawing/input barrier owned by this root, not only a later Compose recomposition. Set it before hiding/reparenting/replacing the target. Cover failures leave private content hidden and readiness false.
- Cancel the existing Activity autofill session on entering/leaving private UI; do not disable the user's installed autofill service. Root traversal tests alone do not prove absence of every provider/WebView direct notification; actual autofill-service and WebView/Compose interaction testing remains a release gate.

### PrivateWindowGuard contract

- Install before first private content can attach. Start Activity recreation/cold-start paths protected; never restore an exception from Bundle or saved Compose state.
- Normal private state: `FLAG_SECURE` set, root structure suppression active, content capture explicitly disabled, safe generic task/window labels. A transient opaque cover is additionally used for transition/failure/teardown.
- Obtain `ContentCaptureManager` from the Activity context; call `setContentCaptureEnabled(false)` before private content, and keep it disabled through the temporary capture exception. A missing manager is absence of that facility, not an error. At targetSdk36 this is a documented independent control; re-review before raising target to37 because the current documentation changes that contract. Keep view-level suppression too. Do not use `removeData` as task-snapshot cleanup.
- API33+: call `Activity.setRecentsScreenshotEnabled(false)` before private display and retain it through arming, recording and protected teardown. There is no getter: evidence means exact Activity/API/invocation ownership, not fabricated readback or a device test. Restore only after safe ordinary content is presented and no private transition remains.
- API31/32: return an explicit legacy-evidence-unavailable capability. `AppTask.setExcludeFromRecents(true)` plus exact `taskId`/root-Intent flag readback is exclusion evidence only. It must never issue `LEGACY_VALIDATED_ISOLATION` on its own.
- `openException` checks exact window/root/target/presentation identity, resumed+focused Activity, all independent protections and `stillAllowed` immediately before clearing only this capture Window's `FLAG_SECURE`. Do not clear other application windows. It returns false on any uncertainty and leaves the cover/protection in place.
- `protectAndStopCapture(): Boolean` keeps its present synchronous shape: true means secure was requested and a sticky native cover/drawing-input barrier was installed on this main-thread turn before any replacement/navigation. It is not a compositor acknowledgement. The cover remains over all replacement content until a separately validated safe presentation; setting `visibility` or reading `window.attributes.flags` alone proves neither drawing nor WindowManager application. An outstanding frame acknowledgement is pending, not false and not a reason to permanently block the host. False is reserved for a real inability to install the local barrier.
- `PrivateCaptureSurfacePort.restoreProtection` uses the existing separate callback for capture-policy settlement: begin protection synchronously, then acknowledge the real owned cover draw/frame submission (or another independently reviewed actual hidden-surface condition). Keep it pending if there is no draw; never convert a timeout into protection success. A frame-commit callback still does not prove global compositor ordering or deletion of older system snapshots. Real WebView/WindowManager ordering is an Android gate. If the actual target can bypass the cover, stop and propose the smallest deferred host-transition result instead of fabricating evidence or widening the synchronous Boolean.
- Register/unregister each app Dialog/Popup as a distinct window/root before showing private contents. Keep these windows secure even while the main capture Window is temporarily nonsecure. A dialog's default inherited secure policy is insufficient when the parent is deliberately cleared. Wrap dialog/ComposePopup content in the same real private root, and control its actual window's secure policy. A missing root/window registration is a blocker for that private UI.
- For the first recording slice, setup/disclosure/record controls are inline. No app-owned Dialog/Popup is allowed during ARMING/ACTIVE: protect/revoke first, then open it. Inventory WebView-native transient presentations separately; an after-the-fact window scan does not prove pre-first-frame protection. Do not claim blanket all-window coverage until this is verified.

### MainActivity composition change

Replace the current direct `ComponentActivity.setContent` host with `setContentView(PrivateContentRoot)` containing one `ComposeView`, then `ComposeView.setContent` with the unchanged app composition. Use ComponentActivity's public content-install path so ViewTree lifecycle, ViewModelStore and SavedStateRegistry owners remain installed; do not create a second Recomposer or new navigation owner. Verify owner lookup from the child and composition disposal on Activity destruction. Maintain existing insets/window behavior. A wrapper installed only around BrowserScreen cannot protect private data in separately rooted dialogs.

### Required first-slice tests

- Ordinary structure delegation unchanged; private autofill/Assist traversal has no child fields even with INCLUDE_NOT_IMPORTANT; returning ordinary restores only after safe presentation.
- Real root and Decor readback, exact Compose1.8.3 owner hierarchy, initial-frame cover, recreation, root replacement, failure while setting protection, and per-dialog registration/disposal.
- Explicit content-capture disable persists while FLAG_SECURE is cleared; independent recents API33 path; API31/32 cannot manufacture suppression evidence.
- No readiness or capture permission from pure flag tests alone. Android/framework tests are still required; no device evidence was generated here.

### Review amendment: exact frame acknowledgement and input revocation

- Every protection activation increments a main-thread protection generation and captures exact Window, DecorView, PrivateContentRoot and target/presentation identities. A completion callback is valid only for that same still-current generation and identity tuple. Replacement, disposal, a newer cover, or renewed capture invalidates earlier callbacks.
- Record in the root's actual draw path that this generation's opaque cover was drawn; only a subsequent real hardware frame submission/commit callback for that generation may acknowledge it. A pre-draw callback, an old frame callback, a frame that never drew the cover, or a software-rendering/no-op registration cannot settle protection. Unsupported/missing acknowledgement remains pending with the cover retained, or uses a separately reviewed actual hidden-surface condition. Do not turn it into success or a permanent failure merely because no frame was available. Physical compositor ordering remains the explicit Android gate.
- The cover is an input-revocation boundary, not merely a clickable child. Set its protection/input generation before callbacks can run; consume touch (including an ongoing gesture), pointer/generic-motion and key dispatch at the real root while covered. Cancel existing interactions, clear focused descendants and dismiss the IME through the owned Window. Do this for each affected root, not only the main Compose child.
- Keep the existing owner-fenced address/query/Go/clear handlers. Feed cover state/generation into their live admission predicate before clearing focus; stale or already-posted IME action callbacks must fail admission. Hiding the IME and clearFocus are best-effort presentation cleanup, not revocation evidence.
- A ViewGroup cannot intercept direct calls to an already-created child InputConnection. The Compose/WebView input owner must therefore invalidate its connection/action generation when covered and reject stale edit/action callbacks; use a small forwarding InputConnection wrapper if the current owner lacks that gate. This is an explicit integration requirement, not a claim that the root alone blocks native IME calls. Until verified, report input containment incomplete and keep overall private readiness false. Ordinary input delegation remains unchanged.
- Tests must include old/new root and generation swaps, callback-before-cover-draw, delayed older commit, software/no-op frame handling, active drag and hardware key, focused Compose and HTML input, and a retained old InputConnection/IME action delivered after covering.

## Smallest Record bridge, after the Runtime writer hands back ownership

One app-layer `PrivateRecordingBridge` should compose the existing policy, Browser target/lease and Record owner. Do not create a second recorder, service, native thread pool, grant store, output pipeline or durable privacy framework. Names below describe proposed app-internal methods, not APIs already implemented.

### Existing attachment points and precise changes

- `SystemBrowserHost.kt`: already supplies `capturePrivateCaptureTarget()`, `isPrivateCaptureTargetCurrent(target)` and `privateCaptureLease(target)`. Target contains the actual session, Entry identity, current document token and actual WebView; URL equality alone is insufficient. Existing main-frame/redirect/history invalidation changes the document token and calls protection before navigation. Reuse these hooks.
- `BrowserScreen.kt` and `MainActivity.kt`: current `onRecording = { navigate(RECORD) }` must branch for private BASIC into same-route protected capture presentation. Retain the same AndroidView node and selected WebView when practical; hide chrome conditionally instead of constructing a second host or blindly removing its parent. If a layout move is unavoidable, do it under the native cover and verify exactly one attached parent before granting surface evidence. Hide address/drafts/tab strip/bookmarks/history/settings/global navigation and unrelated notices. Show generic label, requested audio choice, explicit per-start disclosure, start, stop/save and explicit discard. Other private Views remain hidden and muted. Disable external/fullscreen/file/JS-dialog transitions until protection is restored. Existing host callbacks still invalidate asynchronous page navigation.
- `AndroidSaveRuntime.prepareRecording(...)`: reuse the single execution reservation, destination admission and `CaptureDescriptor(sessionId, generation, audioChoice, profile)`. Add an optional exact private binding at reservation time (or a parallel private entry method delegating to the same reservation body), never a mutable flag inferred later from current browser state. A private reservation freezes descriptor, mode BASIC, target, owner object, Activity generation, requested default-display scope and selected audio. Owner identity cannot be just the reusable task-id string.
- `RecordingConsentController`: keep ephemeral result transport and cancellation tombstone. Expose exact pending request/stage or explicit launch/result events to this bridge. Its current `requestInFlight: Boolean` is not enough to identify an expected consent pause. For private BASIC, `requiresDefaultDisplayRecording(id)` must be true for that exact reservation; ordinary BASIC retains current user-choice behavior. Never inspect hidden result Intent extras or save the result.
- `receiveProjectionGrant`: still validate and offer only once into `ProjectionGrantHandoff` (30s TTL), then start the existing foreground service. The bridge records only acceptance correlation; it does not retain another Intent/token copy. Grant acceptance is distinct from native start. A successful offer does not clear secure.
- `onRecordingServiceReady`: ordinary branch stays unchanged. For the exact private BASIC binding, retain the promoted service and reservation but park before `recorder.admitForeground`, coordinator submission and worker/native launch. Do not block the main thread or spin a native worker while waiting. Resume only once the Activity is resumed/focused, exact target current, isolated surface drawn and independent recents/structure protection established. The binding and `hasPendingRecording(id)` must still match; grant expiry/timeout/service loss cancels this start without retrying the grant.
- Then call policy `projectionAccepted(attempt)`, obtain exact `PrivateCaptureSurfaceEvidence` from the Activity adapter, and call `openForSurface` to get the single-use permit. Only this path clears secure for the selected capture window. Immediately continue the existing submission path with that same immutable private binding. Keep a bounded arming watchdog.
- `AndroidRecordSavePort.record`: existing `lease.tryAcquire()` immediately before native queue submission becomes the private registration boundary. Use the already existing `registerPrivateCaptureOwner(work, permit, ownerIdentity) { register exact queued owner; acquire existing RecordingNativeLease }`. For ordinary work use the original path. Registration is short and synchronous, no native/API acquisition or reentrant callback, and partial registration remains owned on exception. Submit to the existing native executor only after this returns successfully.
- In the native callable, recheck exact binding/descriptor and monotonic private stop state before `ProjectionGrantHandoff.take`, `getMediaProjection`, and `AndroidRecordingSession.run`. A revoked queued owner must acknowledge that it cannot start; executor rejection is evidence only when the job truly was never scheduled. Stop racing queue submission cannot release a source registration prematurely.
- `AndroidRecordingSession`: insert a small app-internal first-native-acquisition observer/checkpoint, not a new capture policy. BASIC `prepareSegmentOutput -> prepareAudio -> AudioRecord.startRecording` precedes final `createCaptureDisplay`. REGION preview creates its VirtualDisplay even earlier. All are covered by the same consumed permit/registered native owner. Notify `nativeStarted(attempt)` on the owner thread after the first actual capture acquisition, with exact identity; PREPARING/FGS start is not that event. The existing observed sample/format/progress rules still determine whether a real recording exists. A policy native-start acknowledgement is not output success. Queue admission never substitutes for the session pre-acquisition gate: pass the same irreversible stop/revoke latch into AndroidRecordingSession and recheck after every slow output/codec preparation returns, before AudioRecord creation and especially startRecording, and before every createVirtualDisplay. nativeStarted is a post-acquisition observation, never permission. Already in-flight calls remain owned for exact cleanup; no permit/source/UI lock crosses a native call.

### Minimal transient bridge state and messages

The one live binding holds `ownerIdentity`, full immutable CaptureDescriptor, target, Activity identity/generation, attempt, `PrivateWorkRegistration`, requested scope, actual pending-consent correlation, service-ready state and optional one-shot permit. No URL/title/profile name/Intent/token is serialized or logged. Binding is not put into SavedStateHandle/rememberSaveable.

The messages needed are only: reservation accepted; exact consent stage launched/completed/cancelled; grant offered; exact service ready/lost; exact surface ready/lost; first native capture acquired; stop requested; actual capture release confirmed/unconfirmed. Each stale/duplicate/wrong-owner event is rejected. Record owner methods remain the authority for publication and resources.

Before consent, register the private lease with `PrivateWorkKind.RECORD_STOP_FINALIZE`. The on-exit callback restores protection and requests stop/finalize of this exact owner. Use `registerPrivateCaptureOwner` at real queue admission to preserve existing lock order: source lease -> permit -> short owner registration. Do not call Android/UI/native work under these locks. A never-queued reservation may complete only after proving no queued worker/grant continuation can still start; a posted cancellation is not proof.

### Protected consent round-trip, narrowly bounded

Current `MainActivity.onPause -> browser.pause()` sets browser foreground=false and invokes `protectAndStopCapture`; `browser.resume()` invokes it again. Blindly using them revokes every private consent attempt. Also `isPrivateCaptureTargetCurrent` intentionally requires foreground. Do not weaken that predicate or keep the entire app falsely foreground during system consent.

Add a lifecycle-specific protection reason/context to the existing composition, used only by Activity pause/focus/resume handling. The only preservable case is the same Activity generation and exact private request actively launching/waiting for the existing AUDIO or PROJECTION consent stage, while policy is CONSENT_PENDING and no permit/native owner exists. During this exception: remain secure and covered/muted, perform ordinary background cleanup, pause WebViews/timers, and retain only pre-start correlation. Do not turn a generic focus loss or `requestInFlight` Boolean into authorization.

A result may arrive before `onResume`; park its offered grant/service under protection. Resume browser foreground and the same protected surface first, then validate the full target and advance policy. A short protected handback state covers the exact already-received result until resumed+focused; it cannot arm during background. Different route/tab/document, denial, launch failure, timeout or Activity destruction/recreation revoke. The nonce proves a pending request, not why pause occurred; onUserLeaveHint is not a Home-only detector. Any lifecycle interruption uses a bounded protected pre-start suspension with zero permit/native acquisition. After resumed+focused+exact-target validation, require a fresh explicit Continue confirmation before arming; without confirmation remain protected until cancellation/timeout. Never infer the interruption was system consent, and never use old consent alone as resumed capture authority. No active/arming recording receives this pause exception.

Private `onDestroy` cancels the exact pending consent even on configuration recreation (`isFinishing` alone is insufficient); the current ordinary controller otherwise retains process-local pending consent. The new Activity starts protected and stops an old private owner; it never inherits its exception. Leave ordinary consent-recreation behavior unchanged.

### Stop, valid output, native drain

- `KEEP_VALID_OUTPUT` maps to the same owner’s `stopAndSave` / `stop(reason)`, not `AndroidSaveRuntime.cancel`, coordinator user-cancel, `OperationContext.cancelToken.cancel`, or `AndroidRecordSavePort.denied` after native capture has begun. Before first capture there may be no valid output; finish the pending reservation cleanly.
- Explicit discard maps to existing cancel/discard only for unpublished work. Later discard monotonically upgrades output disposition without a second native release. Already committed media is never deleted by private exit.
- Current `AndroidRecordSavePort.record` rejects publication if its operation token is cancelled even after successful finalization. Therefore browser source revocation must not cancel this token. SaveCoordinator's current `signalBackgroundPauseAll` and `pauseForBackground` already exclude RECORD; preserve that separation. Network①② keep their own cancel/detach rules.
- Add an exact-owner capture-drained callback to the existing native lease/port owner, fired only after the actual native cleanup body has returned and release is confirmed. `AndroidRecordingSession.releaseResources` covers projection callback unregister, VirtualDisplay, audio/codec/mux/writer, GL and projection.stop; `lease.released(false)` stays quarantined. In the pre-session path, projection.stop must be confirmed too. A UI snapshot, `session = null`, Future cancellation, service destruction, or `currentRecordingId = null` is not this evidence.
- Gate queued callback delivery by exact owner and terminal state so a previously posted projection callback cannot revive or affect a new owner. The drain observer itself must not call arbitrary policy/UI while holding the lease lock.
- The bridge sends actual drain to both the policy stop callback and private source registration completion. Policy separately waits for its real protection acknowledgement. Browser profile retirement still waits actual View/worker/Save/capture drain; no profile deletion callback substitutes for native release. Unconfirmed release keeps the owner quarantined and a recovery state visible.
- Once source capture is truly released, output-only verification/remux/publication can finish through current storage transactions while private browsing exits. Drop target/session/View references from that output-only work. `PrivateSessionLease.register(OUTPUT_ONLY)` deliberately returns null; do not invent a registration to hold the private source open for pure output. Continue existing single-media admission until its normal completion.
- Durable `SaveInput.Capture` already contains no browsing URL or reusable authorization. Preserve that path; never make a fake network source or add private page identifiers to task metadata/filenames/notifications. The output is ordinary explicitly saved media and remains in the library.

## REGION follow-on: exact bounded gap

`AndroidSegmentRecordingRuntime.serviceReady` currently acquires its own existing lease, and its native path consumes ProjectionGrantHandoff before constructing the same AndroidRecordingSession. It needs the equivalent private binding/permit/real-drain hooks before it can be enabled for private REGION. Its authorized-frame preview is already capture and must be gated before the first preview VirtualDisplay, not after crop confirmation. Reuse its current one-projection/one-display/segment pipeline. Do not route a private REGION request into unmodified ordinary serviceReady or fake BASIC scope. Pausing between segments retains projection ownership and is not private drain.

## API31/32 product options and honest limits

The public APIs checked do not provide an API31/32 app-accessible counterpart to API33 recents screenshot suppression. They also do not promise an app can erase all old system thumbnail/snapshot bytes. Changing a theme/task description, covering at exit, readback of FLAG_SECURE, re-entering Overview, or removing a task is not such a promise.

1. **Continue capability gate until validation/product choice.** Keeps private③ in scope, with an explicit unsupported-current-capability reason on these builds rather than silently deleting it. This is the present integration status, not the proposed permanent product outcome.
2. **Informed legacy capture exception, if the user approves the narrower privacy promise.** Same-route BASIC capture can temporarily permit pixels with the existing full-screen disclosure plus an explicit API31/32 snapshot warning. Exclude the exact current AppTask before lifting secure, use the sticky cover/secure restoration on every departure, and keep it excluded until a separately verified safe ordinary presentation. Validate normal Recents nonexposure on the actual supported systems. The warning must state that a task thumbnail may be produced/retained during recording and ESV cannot guarantee removal of earlier system copies. User approval changes the promise; it does not justify issuing `LEGACY_VALIDATED_ISOLATION`. Add a distinct explicit acknowledged-risk capability/disclosure state in policy if chosen.
3. **Dedicated excluded capture task, only as a separately reviewed follow-on.** This keeps the ordinary task's recent-card behavior independent and can end via `AppTask.finishAndRemoveTask`. It adds Activity/WebView ownership and lifecycle transfer work, so it is not the smallest first slice. The method removes the task from Recents; it does not document secure erasure of historical snapshot storage. It can improve tested UI nonexposure but does not eliminate the need for a truthful residual-risk statement if no-snapshot creation/erasure is required.

No proposal here accepts the legacy risk for the user, permanently drops API31/32, claims screenshots can be isolated to ESV, or changes the approved API31 minimum. Parent owns the product decision. If that decision is needed, bundle it once with the exact proposed mitigation/remaining risk; do not ask vague permission to weaken privacy.

## Device and integration acceptance gates

- Real BASIC private video is visible and playable, not a successful black file; silent/internal-audio variants; only selected private page and essential controls; no other private tab audio/title/draft.
- No capture/audio before permit; revoke before/after queue registration, grant offer/service ready and first audio/VD creation; partial acquisition, native hang and rejection; actual native release before private profile cleanup.
- Consent allow/deny/audio-deny, result-before-resume, Home while consent pending, late result, repeated click/cancel, rotation/recreation/process restart, ordinary capture conflict, and no grant reuse.
- Stop/Back/tab/document/redirect/history/route switch, notification shade/focus loss, Home/Recents, screen lock, projection revocation, renderer crash and service loss restore local protection before new content and keep valid requested output. Explicit discard affects only unpublished output.
- Exact Compose1.8.3/WebView autofill and content-capture tests, forced include-not-important structure request, every dialog/popup root, native overlay timing, cover frame/WindowManager ordering.
- API31 and32: exact task exclusion/restore/removal and stale-thumbnail observations under the chosen explicit product promise. API33+: recents suppression during active recording and teardown. Neither test observations nor API calls are forensic erasure guarantees.
- API34+: fresh explicit-default-display consent factory, actual content/geometry behavior and OEM opt-out override. Equal captured dimensions do not identify the chosen source. Do not claim app-only/video-box capture from a default-display buffer or guess hidden intent fields. Scope mismatch/unknown state remains a capture gate.
- Ordinary BASIC, proportional REGION/authorized preview, normal consent recreation, Save①②, output verification/publication and library retention remain regression tests. Compile/unit results alone cannot close any Android gate.

## Official evidence (checked 2026-10-14)

- Activity `setRecentsScreenshotEnabled`, added API33, affects recents representation independently of other screenshots: https://developer.android.com/reference/android/app/Activity#setRecentsScreenshotEnabled(boolean)
- AppTask exclusion modifies the root Intent flag; task removal finishes activities/removes the recent entry, without a snapshot-erasure contract: https://developer.android.com/reference/android/app/ActivityManager.AppTask#setExcludeFromRecents(boolean) and https://developer.android.com/reference/android/app/ActivityManager.AppTask#finishAndRemoveTask()
- Autofill hierarchy dispatch permits custom ViewGroup handling of INCLUDE_NOT_IMPORTANT; setting own AutofillId is required when not calling super: https://developer.android.com/reference/android/view/View#dispatchProvideAutofillStructure(android.view.ViewStructure,int)
- ContentCaptureManager explicit disable is separate from secure-window behavior at current target36: https://developer.android.com/reference/android/view/contentcapture/ContentCaptureManager#setContentCaptureEnabled(boolean)
- MediaProjection fresh one-use consent, single-app sharing, explicit default-display opt-out and OEM override warning: https://developer.android.com/media/grow/media-projection

The source tree changed concurrently in network-only areas. Function names and described current behavior were inspected directly; line numbers are intentionally not used as stable contracts. No source/runtime/device acceptance is implied by this design.

### Required Record bridge acceptance cases

- Block output/codec preparation, revoke, then release: AudioRecord.startRecording and VirtualDisplay creation remain uncalled.
- Park service-ready, then expire grant or recreate Activity: no native start.
- Return after an unknown pause without explicit Continue: no capture.
- KEEP_VALID_OUTPUT followed by actual native drain still permits the same output owner to verify and publish.
