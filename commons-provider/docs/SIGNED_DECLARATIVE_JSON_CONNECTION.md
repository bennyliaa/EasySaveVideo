# Signed finite JSON candidates: host-admitted integration

This connects the finite JSON mapper to the existing ProviderRepository, its version and policy anchors, fixed self-test, probation/quarantine, and update runtime. It is an offline-capable host SPI; no production JSON source, endpoint, trust root, downloadable script, or additional App registration is provided.

## Compatibility and admission

- Legacy Commons ESVP v1 and ESVS v1 bytes, 8 KiB envelope / 4 KiB payload bounds, signature domains and built-in behavior remain unchanged.
- A host chooses a fixed immutable ProviderTarget: ID, implementation version, source label, finite limits and fixed expected self-test vectors. Packages cannot choose directories, keys, endpoints, callbacks, privileges or new targets.
- New JSON targets use ESVP v2, schema 2, candidate-only kind 1: maximum 24 KiB envelope, 20 KiB payload, 16 KiB rule bytes. The complete manifest and raw rule bytes are authenticated before compilation; full SHA-256, schema/rule version, exact spec/runtime and minimum App compatibility are checked.
- Target-aware ESVS v2 authenticates independent repository policy. Both verifiers share the same fixed target object. Package and policy keys remain separate. The original mutation owner is reused. Commons records remain format 3 byte-for-byte; JSON records use format 4 with one fixed 16-byte non-secret random incarnation after the generation. Record budgets include the extra 16 bytes and the target's bounded envelopes. Old JSON format-3 records are fully authenticated before migration through the original intent/fsync/atomic-publication transaction. Failed migration stays disabled with evidence intact; probation is never silently confirmed.
- A new target starts disabled without a signed compiled plan. A failed self-test cannot activate or raise the package high-water mark. The actual authenticated plan must produce exactly the host vectors; three real conclusive successes promote a candidate through the existing health owner.
- ProviderRepositoryOwner admits at most two fixed candidate target/directory pairs alongside the existing legacy entry. The subsequent bounded HTTP increment adds an explicit second candidate kind to this same owner; see BOUNDED_HTTP_HTML_CANDIDATES.md. No JSON targets are registered by production assembly in this increment. A host assembly uses one existing UpdateRuntime per admitted target; arbitrary trusted object construction is not a global concurrency boundary.

## Runtime and publication

SignedJsonVideoSearchProvider preserves the host-injected pure-JSON response-byte contract as a compatibility facade over the shared SignedRuleVideoSearchProvider. The separate bounded HTTP kind uses that same lifecycle with its own fixed host endpoint; kind 1 still cannot supply requests or endpoints. Each request acquires one repository lease against the Coordinator's exact captured descriptor. Its immutable plan, limits, source label, health observation and authority all come from that owner. Bare search cannot bypass acquisition.

The descriptor version is 64 lower-case hex SHA-256 of canonical frame v2: big-endian byte-length-prefixed UTF-8 domain `esv-signed-json-authority`, big-endian int frame version 2, fixed 16 raw incarnation bytes, byte-length-prefixed UTF-8 target ID and implementation version, 32-byte package digest, 32-byte rule digest, one byte policy-present flag and optional 32-byte policy digest, then big-endian long generation. Healthy promotion keeps the generation. Every actual authority change invalidates the old view synchronously under the same short repository authority gate.

Bytes are bounded while reading, then parsed by the finite mapper. Output remains only source-reported CandidateUrl metadata. ValidationPipeline must explicitly retain unvalidated candidates or use an independent validator. No mapper result is RawVideoResult, playback evidence or download rights.

The isolated runtime retains existing actual-worker/cancellation-drain slot semantics. A completed worker releases its physical source slot before invoking the callback, permitting same-source automatic next-page execution. The resource lease closes exactly once after both worker and callback finish, including cancellation before a late acquire. The read-only authority view survives normal request close and its deadline; pending data remains valid only while the repository identity and package/policy expiry remain current.

Coordinator checks original authority before store commit and again after successful commit before publishing session progress, pending cards and verification summary. The authority gate performs only bounded memory work; it never wraps database I/O, clocks, cancellation, source calls or listeners. Old physical records may remain but are not current authority. A pre-commit-authorized independently verified historical result may remain after a successful database commit even if revocation/cancellation wins the later gate. Unverified candidates never become history through that exception. Reads and explicit verification prune invalid authority and cannot borrow a newer same-ID plan for an older candidate.

## Pagination and remaining production gates

The mapper extracts one opaque token, never follows it as a URL. The SPI supplies it to the same host response port. JSON targets use the existing DURABLE progress row keyed by profile/provider/query, with the full stable descriptor token in its existing providerVersion field. Normal repository reopen retains the incarnation and exact token. A new empty repository gets a fresh incarnation, so reinstalling the same signed bytes cannot reuse another repository's cursor. Format-3 migration changes the token conservatively; old-format cursors restart rather than being silently rebound. The Coordinator's existing six-request round, repeated-cursor and no-new-result guards apply. Cursor lifetime is bounded by five minutes and owner expiry.

Before inspecting restored progress, the Coordinator obtains an exact read-only view from the original repository, outside any store transaction. This does not acquire request resources, consume health observations or authorize new demand. Old pending data is invalidated before warming a new identity; retired sources cannot automatically fetch a new view on status polling. Restore preserves explicit-query/configuration gates. Incognito remains isolated in its existing in-memory store.

The repository's real file reopen and migration are tested. Recovery-policy tests serialize explicit bounded synthetic checkpoint/progress/Seen rows and restore them into a new InMemoryDiscoveryStore, then use new real runtime and Coordinator instances. They do not reuse the old map or request objects. This is not an Android SQLite implementation, crash-durability simulation, or a claim that device cross-process restore has been tested. The unchanged Android progress table already stores the required identity, query, schema and expiry fields; a device-backed SQLite reopen check remains a separate validation gate. A coherent replay of the entire repository plus matching discovery image is still outside the local incarnation's protection.

Before shipping a live JSON provider, the host still must select real trusted package/policy roots, fixed target and test vectors, admitted service configuration, and a transport enforcing TLS, host/redirect/DNS-address policy, deadlines and cancellation. None of these are inferred from rule JSON. General scripting, arbitrary regex/expression evaluation, generic network capabilities, entitlements, and remote package registration are outside this finite increment.

Tests are synthetic, offline and key-isolated. The integration tests exercise two different signed targets through the actual registry, isolated runtime, validation pipeline and Coordinator, including two-page execution, real health promotion, budgets, expiry, source isolation and revocation around store publication. The durable increment additionally covers stable reopen, exhausted progress, fresh-repository rejection, package/policy changes, exact rollback, mismatched cursor/query/profile, fresh-clock view acquisition, and recovery gates. Test execution is recorded separately by the central build owner.
